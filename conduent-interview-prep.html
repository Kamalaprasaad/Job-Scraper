Prepared Answers

1A pod is in CrashLoopBackOff. What do you check?

Kubernetes Production triage

I first confirm whether the container is crashing because of application error, bad config, dependency failure, resource pressure, failed probes, or a bad rollout.

  1. Check pod status, restart count, node, and age.
  2. Describe the pod and read Events for image pull errors, OOMKilled, probe failures, or scheduling issues.
  3. Check current logs and previous crash logs because the container may restart too quickly.
  4. Compare recent deployment changes: image tag, ConfigMap, Secret, env vars, resource limits, and probes.
  5. If needed, roll back the deployment after confirming it is safer than continuing the failed release.
kubectl get pods -n <namespace> -o wide
kubectl describe pod <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace> --previous
kubectl get events -n <namespace> --sort-by=.lastTimestamp
kubectl rollout history deployment/<deployment> -n <namespace>
Interview closing line: "I would not just restart blindly. I would capture logs and events first, because the first evidence usually explains the real failure."

2A Kubernetes service is not reachable. How do you troubleshoot?

Kubernetes networking Service discovery

I isolate whether it is a pod readiness issue, selector mismatch, wrong port mapping, DNS issue, ingress/load balancer issue, or network policy restriction.

  1. Check service definition, type, port, targetPort, and selector labels.
  2. Check endpoints. If there are no endpoints, the service is not matching ready pods.
  3. Verify pods are Ready and their labels match the service selector.
  4. Test DNS and connectivity from another pod inside the same namespace.
  5. Check ingress, load balancer, firewall rules, and network policies for external access.
kubectl get svc,endpoints -n <namespace>
kubectl describe svc <service> -n <namespace>
kubectl get pods -n <namespace> --show-labels
kubectl describe ingress <ingress> -n <namespace>
kubectl get networkpolicy -n <namespace>

If endpoints are empty, I focus on labels, readiness probes, and pod health. If endpoints are present, I test DNS, ports, application listener, and network path.

3A deployment failed after a Helm release. What do you do?

Helm Release safety

I treat it as a release incident: confirm the failed revision, inspect what changed, check Kubernetes events/logs, and roll back if user impact or risk is high.

  1. Check Helm release status and revision history.
  2. Review rendered values and compare the failed release with the previous working release.
  3. Check deployment rollout status, pods, events, and logs.
  4. If the issue is clear and low risk, fix values and redeploy. If production is impacted, roll back first.
  5. After recovery, document root cause and add validation to the pipeline if possible.
helm list -n <namespace>
helm status <release> -n <namespace>
helm history <release> -n <namespace>
kubectl rollout status deployment/<deployment> -n <namespace>
helm rollback <release> <revision> -n <namespace>
Strong wording: "For production, my first priority is service recovery. Root cause can continue after the platform is stable."

4An API returns HTTP 500. Walk me through your steps.

API support Tomcat

A 500 means the server failed while processing the request, so I use request evidence to trace from client input to application logs, dependencies, and recent changes.

  1. Confirm the exact endpoint, request payload, timestamp, user/account, correlation ID, and frequency.
  2. Check application and Tomcat logs around the timestamp for stack trace or exception message.
  3. Check whether the issue is isolated to one payload/user or broad across the API.
  4. Validate dependencies: database query, downstream API, credentials, connection pool, timeout, disk, memory, CPU.
  5. Check recent deployment/config changes and compare with a working request.
  6. Mitigate, communicate status, and create RCA with cause, impact, fix, and prevention.

Good interview line: "I do not start by guessing code changes. I start with correlation ID, timestamp, logs, and dependency checks."

5A transaction table has 4 years of data and queries are slow. How do you optimize?

SQL Oracle/MySQL

I first identify the actual query pattern and execution plan. Then I tune predicates, indexes, statistics, and partitioning based on how the table is accessed.

  1. Find the slow SQL, bind values, frequency, and whether it scans old data unnecessarily.
  2. Use EXPLAIN PLAN or EXPLAIN ANALYZE to check full table scans, joins, sort, and index usage.
  3. Avoid SELECT *; select only needed columns and filter early.
  4. Add or adjust composite indexes based on common filters like status, date, user ID, or transaction ID.
  5. Use date-based partitioning for large historical transaction data so recent queries scan fewer partitions.
  6. Archive older data if the business only needs recent data for operational queries.
  7. Refresh statistics and validate improvement with before/after execution time and plan comparison.
SELECT user_id, COUNT(*) AS failure_count
FROM transaction_history
WHERE status = 'FAILED'
  AND transaction_date >= :start_date
  AND transaction_date < :end_date
GROUP BY user_id
HAVING COUNT(*) > 3;

6Difference between index and partitioning?

Database design Optimization

An index helps the database find rows faster. Partitioning physically divides a large table into smaller logical pieces, often by date or range.

  1. An index is like a lookup structure for columns used in WHERE, JOIN, ORDER BY, or GROUP BY.
  2. Partitioning divides the table into manageable sections, such as monthly or yearly partitions.
  3. Indexes reduce row lookup cost, but they add overhead to inserts, updates, deletes, and storage.
  4. Partitioning improves large-table manageability, archival, partition pruning, and maintenance.
  5. They can work together: a partitioned transaction table can also have local or global indexes.
Interview phrase: "We usually do not call an index directly from application code. We write selective predicates and maintain good indexes and statistics so the optimizer chooses the best path."

7How do you process a 5 million record file in Python?

Python Batch processing

I would not load the whole file into memory. I would stream it or process it in chunks, validate records, batch writes, and make the process restartable.

  1. Understand file type: CSV, JSON lines, fixed-width, XML, or nested JSON.
  2. Read line by line or in chunks instead of loading the full file.
  3. Validate each record and write rejected records to a separate error file with reason.
  4. Use batch inserts or batch API calls to avoid one transaction per row.
  5. Add checkpointing so the job can restart from the last successful offset or batch.
  6. Log counts: total, success, failed, skipped, duration, and memory usage.

8How do you validate AI-generated incident summaries?

AI operations Governance

I validate AI summaries against source evidence: logs, alerts, timestamps, tickets, runbooks, and actual remediation steps. The AI output is a draft, not the final truth.

  1. Ground the model with approved source data instead of asking open-ended questions.
  2. Require structured output: impact, timeline, probable cause, evidence, action taken, next step.
  3. Ask the model to say "not enough evidence" when logs or facts are missing.
  4. Compare the summary with monitoring data, ticket notes, and engineer actions.
  5. Use human review before customer-facing RCA or production remediation.
  6. Track accuracy by comparing AI summaries with final RCA and known incident categories.
Say this clearly: "To reduce hallucination, I ground the AI with logs and approved runbooks, require evidence, and keep human approval for production actions."

9What is RAG and where would you use it in IT operations?

RAG AIOps

RAG means Retrieval-Augmented Generation. The system retrieves relevant internal knowledge first, then gives that context to the language model so the answer is grounded in company data.

  1. Input: incident description, alert, log snippet, error code, or ticket text.
  2. Retrieval: find similar incidents, runbooks, KB articles, deployment notes, and known error patterns.
  3. Generation: produce probable cause, next troubleshooting steps, severity suggestion, and source references.
  4. Validation: show evidence and confidence, then require engineer review for high-risk actions.

I would use RAG for incident triage, ticket summarization, runbook search, known-error matching, alert correlation, and drafting RCA notes.

10Tell me about a production incident where you communicated with client/internal teams.

STAR Communication

Use a calm incident story. Focus less on heroics and more on ownership, communication, evidence, and prevention.

Situation: In my current production support role, we had an issue where a set of transaction/API requests started failing and users were seeing errors during processing.

Task: My role was to triage the incident, identify whether it was application, data, or dependency related, keep internal stakeholders updated, and help restore processing.

Action: I collected the timestamp, affected request details, and error messages. I checked application logs, database records, and compared failed transactions with successful ones. I updated the internal team with findings, documented ticket notes clearly, and escalated with evidence when the issue required another team.

Result: We isolated the failure pattern, restored processing, and documented the root cause and next-step prevention in the ticket/runbook so similar incidents could be handled faster in the future.
