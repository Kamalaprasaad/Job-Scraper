Python Patterns

1. Process a large CSV without loading everything

5 million records Memory safe

Use this when they ask about processing large transaction files. 

import csv

def process_file(path, batch_size=5000):
    batch = []
    total = success = failed = 0

    with open(path, newline="", encoding="utf-8") as file:
        reader = csv.DictReader(file)

        for row in reader:
            total += 1
            try:
                record = validate_and_transform(row)
                batch.append(record)
            except ValueError as error:
                failed += 1
                write_reject(row, str(error))
                continue

            if len(batch) == batch_size:
                success += process_batch(batch)
                batch.clear()

    if batch:
        success += process_batch(batch)

    return {"total": total, "success": success, "failed": failed}

Interview line: "I stream or chunk the file, validate rows, batch writes, log rejects, and make the job restartable."

Generator Low memory 
def read_transactions(path):
    with open(path, encoding="utf-8") as file:
        for line_number, line in enumerate(file, start=1):
            line = line.strip()
            if not line:
                continue

            try:
                yield parse_transaction(line)

for transaction in read_transactions("transactions.txt"):

Say: "A generator lets me process one record at a time instead of keeping millions of records in memory."

3. Retry an API call safely

API support Timeouts 
import time
import requests

def call_api(url, payload, retries=3, timeout=10):
    for attempt in range(1, retries + 1):
        try:
            response = requests.post(url, json=payload, timeout=timeout)
            response.raise_for_status()
            return response.json()
        except requests.RequestException as error:
            if attempt == retries:
                raise

            wait_seconds = 2 ** attempt
            log_warning(f"API failed on attempt {attempt}: {error}")
            time.sleep(wait_seconds)

Production note: only retry idempotent operations or requests with safe duplicate handling.

4. Parse logs and count errors

Log analysis Incident triage 
from collections import Counter

def top_errors(log_path):
    counter = Counter()

    with open(log_path, encoding="utf-8", errors="replace") as file:
        for line in file:
            if "ERROR" not in line:
                continue

            if "timeout" in line.lower():
                counter["timeout"] += 1
            elif "connection" in line.lower():
                counter["connection"] += 1
            elif "ora-" in line.lower():
                counter["oracle"] += 1
            else:
                counter["other"] += 1

    return counter.most_common()

Say: "For incident triage, I summarize repeating error patterns first, then inspect sample stack traces and timestamps."

5. Checkpoint long-running batch work

Restartable job Batch support 
def load_checkpoint(path="checkpoint.txt"):
    try:
        with open(path, encoding="utf-8") as file:
            return int(file.read().strip())
    except FileNotFoundError:
        return 0

def save_checkpoint(offset, path="checkpoint.txt"):
    with open(path, "w", encoding="utf-8") as file:
        file.write(str(offset))

start_at = load_checkpoint()

for index, record in enumerate(read_transactions("transactions.txt"), start=1):
    if index <= start_at:
        continue

    process_record(record)

    if index % 1000 == 0:
        save_checkpoint(index)

Say: "Checkpointing prevents a failed batch from restarting from zero."

def insert_transactions(connection, rows):
    sql = """
        INSERT INTO transaction_stage

            (:transaction_id, :user_id, :status, :payment_amount)

SQL Patterns

1. Users with more than three failures

GROUP BY HAVING 
SELECT user_id, COUNT(*) AS failure_count
FROM transaction_history
WHERE status = 'FAILED'
GROUP BY user_id
HAVING COUNT(*) > 3;

Say: "WHERE filters rows before grouping. HAVING filters grouped results."

2. Failures by error in a date range

Date filter RCA 
SELECT exception_message, COUNT(*) AS failure_count
FROM transaction_history
WHERE status = 'FAILED'
  AND transaction_date >= :start_date
  AND transaction_date < :end_date
GROUP BY exception_message
ORDER BY failure_count DESC;

Say: "For production triage, I group by exception to find the dominant failure pattern."

3. Latest transaction per user

Window function ROW_NUMBER 
SELECT user_id, transaction_id, status, transaction_date
FROM (
    SELECT
        user_id,
        transaction_id,
        status,
        transaction_date,
        ROW_NUMBER() OVER (
            PARTITION BY user_id
            ORDER BY transaction_date DESC
        ) AS rn
    FROM transaction_history
) ranked
WHERE rn = 1;

Say: "ROW_NUMBER helps pick the latest record per user without messy self-joins."

4. Find duplicate transaction IDs

Data quality Duplicate check 
SELECT transaction_id, COUNT(*) AS duplicate_count
FROM transaction_history
GROUP BY transaction_id
HAVING COUNT(*) > 1;

Say: "For data issues, I first quantify the bad records before proposing correction."

7. Four years of transaction data

Partitioning Archive 
-- Conceptual Oracle range partitioning example
CREATE TABLE transaction_history (
    transaction_id NUMBER,
    user_id NUMBER,
    status VARCHAR2(30),
    transaction_date DATE,
    payment_amount NUMBER
)
PARTITION BY RANGE (transaction_date) (
    PARTITION p_2025_q1 VALUES LESS THAN (DATE '2025-04-01'),
    PARTITION p_2025_q2 VALUES LESS THAN (DATE '2025-07-01'),
    PARTITION p_future VALUES LESS THAN (MAXVALUE)

Say: "For large time-based data, partitioning helps pruning, archival, and maintenance. It is not a substitute for good predicates and indexes."

Oracle / PL/SQL Talking Points

Basic controlled PL/SQL block

BEGIN
    UPDATE transaction_history
    SET status = 'READY_FOR_REPROCESS'
    WHERE transaction_id = :transaction_id
      AND status = 'FAILED';

    IF SQL%ROWCOUNT = 1 THEN
        COMMIT;
    ELSE
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20001, 'Unexpected row count');
    END IF;
EXCEPTION
    WHEN OTHERS THEN
        ROLLBACK;
        RAISE;
END;

Say: "I use row-count validation because production changes should affect exactly the expected rows."

PL/SQL points to remember

  • SQL%ROWCOUNT tells how many rows the last DML changed.
  • COMMIT makes changes permanent; ROLLBACK reverses uncommitted work.
  • Use bind variables instead of string-built SQL where possible.
  • For production, test with SELECT first and document approval.
  • Never hide errors silently; log and re-raise when appropriate.
