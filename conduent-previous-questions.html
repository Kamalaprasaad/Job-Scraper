3If Kubernetes has a problem, what commands would you use?

Kubernetes Troubleshooting
They want to know whether you understand the troubleshooting flow, even if your current environment is mostly VM/Azure based.
I would first identify whether the issue is with one pod, one deployment, one namespace, or the wider cluster. Then I would check pod status, describe output, logs, previous crash logs, events, resources, services, endpoints, and rollout history. 
kubectl get pods -n <namespace> -o wide
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace>
kubectl logs <pod> -n <namespace> --previous
kubectl get events -n <namespace> --sort-by=.lastTimestamp
kubectl top pods -n <namespace>
kubectl get svc,endpoints,ingress -n <namespace>
kubectl rollout history deployment/<deployment> -n <namespace>
Good honesty line: "My current production work is more VM/Azure based, but I understand the Kubernetes troubleshooting path and I have been preparing specifically around pods, deployments, services, Helm, events, and rollbacks."

6How would you process a file with 5 million records in Python?

Python Large files
They are testing memory awareness, batching, error handling, and restartability.
I would avoid loading the entire file into memory. I would stream the file line by line or process it in chunks, validate each record, write rejected rows separately, process database/API writes in batches, and add checkpointing so the job can restart from the last successful batch. 
import csv

batch = []
batch_size = 5000

with open("transactions.csv", newline="", encoding="utf-8") as file:
    reader = csv.DictReader(file)
    for row in reader:
        batch.append(transform(row))

        if len(batch) == batch_size:
            process_batch(batch)
            batch.clear()

if batch:
    process_batch(batch)

7Write a query to find users with more than three failed transactions.

SQL Aggregation
They are checking basic SQL correctness: WHERE, GROUP BY, HAVING.
SELECT user_id, COUNT(*) AS failure_count
FROM transaction_history
WHERE status = 'FAILED'
GROUP BY user_id
HAVING COUNT(*) > 3;
If the table is large, I would usually add a date range so the query only scans the relevant operational window. 
SELECT user_id, COUNT(*) AS failure_count
FROM transaction_history
WHERE status = 'FAILED'
  AND transaction_date >= :start_date
  AND transaction_date < :end_date
GROUP BY user_id
HAVING COUNT(*) > 3;

8Do you need an index? How do you use it in code?

Indexing Optimizer
They are checking whether you know indexes are database structures chosen by the optimizer, not usually called directly in application code.
If the query frequently filters by status and transaction date and groups by user ID, I would consider a composite index based on the actual query pattern, for example status, transaction date, and user ID. In normal application code, I do not call the index directly. I write selective predicates, avoid functions on indexed columns when possible, keep statistics updated, and verify with the execution plan that the optimizer uses the right access path. 
-- Example only; final order depends on selectivity and query patterns.
CREATE INDEX idx_txn_status_date_user
ON transaction_history (status, transaction_date, user_id);

9If the table has 4 years of data, how would you optimize it?

Oracle/MySQL Performance
They want table-level thinking: indexing, partitioning, archival, statistics, and query design.
I would first check the execution plan and query pattern. For a transaction table with years of data, I would consider date-based partitioning, such as monthly or quarterly partitions, so recent operational queries can prune older partitions. I would also archive old data if the business does not need it in the hot table, maintain the right indexes, refresh statistics, and avoid unnecessary columns or unbounded date searches.
  • Use date filters in queries.
  • Partition by transaction date when the table is very large.
  • Archive historical data based on retention policy.
  • Use composite indexes for common access patterns.
  • Review execution plans before and after tuning.

12How do you prevent hallucination in AI outputs?

Responsible AI RAG
This is a key recovery point from the first interview. Answer crisply.
I reduce hallucination by grounding the model with approved source data such as logs, runbooks, knowledge base articles, and ticket history. I ask the model to cite evidence, return structured output, and say "not enough information" when the evidence is missing. For production actions or customer-facing RCA, I keep human review and validation against source systems.
Do not say anything like "give the model sleep time." Say "grounding, evidence, source citations, structured output, and human review."

13What is RAG and how would you use it for IT operations?

RAG AIOps
RAG means Retrieval-Augmented Generation. Instead of asking the AI to answer from general memory, the system first retrieves relevant internal documents, tickets, runbooks, logs, or known-error articles. Then the model generates an answer using that retrieved context. In IT operations, I would use RAG for ticket triage, finding similar incidents, summarizing logs, recommending runbook steps, alert correlation, and drafting RCA notes with references. 
Incident text/logs -> retrieve similar tickets/runbooks -> LLM summary
                 -> probable cause + next checks + evidence links
                 -> engineer validation before production action
